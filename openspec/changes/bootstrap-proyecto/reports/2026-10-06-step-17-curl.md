## 17.3 Base de datos no disponible

**a) PostgreSQL parado** (`docker compose stop`, conexión rechazada):

```
$ curl -i http://localhost:3000/api/health
HTTP/1.1 503 Service Unavailable
Content-Type: application/json; charset=utf-8

{"success":false,"error":{"code":"DATABASE_UNAVAILABLE","message":"La base de datos no está disponible"}}
[tiempo total: 0,03 s]
```

El log del backend contiene `"msg":"Fallo al comprobar la conexión con la base de datos"` con el error; la respuesta no incluye host, puerto, versión ni traza.

**b) PostgreSQL colgado** (`docker compose pause`, la conexión no responde):

```
$ curl -i http://localhost:3000/api/health
HTTP/1.1 503 Service Unavailable

{"success":false,"error":{"code":"DATABASE_UNAVAILABLE","message":"La base de datos no está disponible"}}
[tiempo total: 2,01 s]
```

El 503 llega a los 2 s por el timeout propio del ping, sin esperar a los 10 s del timeout de petición. Tras `docker compose start` / `unpause`, la misma petición vuelve a responder `200`.

**Observación y corrección:** en la primera ejecución, el caso b) no dejaba nada en el log: gana el timeout de `CheckHealth` antes de que el adaptador reciba un error. A petición del usuario se añadió a la spec (`service-health`), al diseño (D1) y a las tareas (6.3 y 6.4) que `CheckHealth` registre un aviso al saltar el timeout, mediante un puerto de log propio de la capa de aplicación. Tras implementarlo con TDD, la misma prueba produce:

```
con la base colgada: 503 en 2,02 s
{"level":"warn","timeoutMs":2000,"msg":"La comprobación de la base de datos ha superado el tiempo máximo"}
```

## 17.6 A través del proxy de Vite (`npm run dev`)

```
$ curl -i http://localhost:5173/api/health
HTTP/1.1 200 OK
content-type: application/json; charset=utf-8

{"success":true,"data":{"status":"ok","database":"up"}}

$ curl -o /dev/null -w "%{http_code}" http://localhost:5173/api/does-not-exist
404
```

Al cerrar `npm run dev` no quedan procesos ni puertos (3000, 5173) ocupados.

### Incidencia encontrada y corregida

En el primer intento, `npm run dev` (backend y frontend en paralelo con `concurrently`) dejaba el proxy respondiendo `502`: el backend no llegaba a escuchar, sin ningún error ni socket abierto. Diagnóstico aislando variables, con ejecuciones de 20 s:

| Combinación | Resultado |
|---|---|
| `tsx watch` solo (`npm run dev -w backend`) | Escucha |
| `concurrently` + `tsx watch` | **No escucha** (se cuelga antes de ejecutar el servidor) |
| `concurrently` + `tsx` sin watch | Escucha en 4 s |
| `concurrently` + `node --watch --import tsx` | Escucha en 4 s y recarga al cambiar `src/app.ts` |

Corrección: el script `dev` del backend pasa a `node --watch --env-file-if-exists=.env --import tsx src/server.ts` (watcher nativo de Node 24, tsx solo como cargador). Se actualizó primero `design.md` (D3) y después el script. Además, en el primer intento quedaron procesos huérfanos (el `tsx watch` padre del backend de 17.1), porque se cerró solo el proceso que escuchaba; desde entonces se cierran árboles completos (`taskkill /T`).

## 17.8 Cuerpo rechazado por su tamaño o su codificación (2026-10-07)

Añadido tras la revisión adversarial: antes de la corrección, los tres casos respondían `500 INTERNAL_ERROR` y dejaban una entrada `error` en el log (`PayloadTooLargeError`, `UnsupportedMediaTypeError`). Backend de desarrollo arrancado con `npm run dev -w backend`; `big.json` es un JSON de 103 435 bytes (límite de `express.json()`: 100 KB).

```
$ curl -i -X POST -H "Content-Type: application/json" --data-binary @big.json http://localhost:3000/api/health
HTTP/1.1 413 Payload Too Large
Content-Type: application/json; charset=utf-8

{"success":false,"error":{"code":"PAYLOAD_TOO_LARGE","message":"El cuerpo de la petición supera el tamaño máximo permitido"}}

$ curl -i -X POST -H "Content-Type: application/json; charset=latin-9" -d '{}' http://localhost:3000/api/health
HTTP/1.1 415 Unsupported Media Type
Content-Type: application/json; charset=utf-8

{"success":false,"error":{"code":"UNSUPPORTED_MEDIA_TYPE","message":"La codificación del cuerpo de la petición no está soportada"}}

$ curl -i -X POST -H "Content-Type: application/json" -H "Content-Encoding: compress-unknown" -d '{}' http://localhost:3000/api/health
HTTP/1.1 415 Unsupported Media Type
Content-Type: application/json; charset=utf-8

{"success":false,"error":{"code":"UNSUPPORTED_MEDIA_TYPE","message":"La codificación del cuerpo de la petición no está soportada"}}
```

El log del backend solo contiene la línea de arranque (`"msg":"Backend escuchando"`): ninguna entrada con nivel `error`. Al terminar se cerró el árbol de procesos (`taskkill /T`) y el puerto 3000 quedó libre.
